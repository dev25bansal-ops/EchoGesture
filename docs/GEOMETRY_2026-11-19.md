# Input geometry: what it does and does not buy

Measured 2026-11-19 over the full 1,255-clip test set, live extraction (no
caches), every configuration scored through the real pipeline —
`read_frames → detect_hands → build_features → 9 TFLite members → mean logit →
argmax` — with refusals from `main._require_hand_coverage` counted **wrong**,
which is the honest end-to-end treatment.

## Accuracy

| geometry | end-to-end | on-success | 95% CI | vs native |
|---|---|---|---|---|
| **native** (`size=None`) | **84.94%** | 85.69% | ±1.98 | — |
| **512 letterbox** | **85.10%** | 85.65% | ±1.97 | **+0.16 pp, p=0.91 — TIE** |
| 512 squash | 81.59% | 84.07% | ±2.14 | −3.35 pp, p=0.0003 |
| 384 squash | 81.36% | 83.89% | ±2.15 | −3.59 pp, p=0.0001 |
| 256 squash | 81.51% | 83.58% | ±2.15 | −3.43 pp, p=0.0004 |

Two things follow, and they point in opposite directions from what the repo
previously believed:

**1. Squash costs ~3.4 points — real, but not 8.43.** Every squash geometry is
decisively worse than native (p < 0.001). But the mechanism is mostly
**coverage**, not recognition: squash yields 25–31 low-coverage refusals against
5–7 for native, because distorting a non-square frame to a square makes MediaPipe
find hands in fewer frames. On the clips it *does* accept, 256-squash reaches
83.58% against native's 85.69%.

**2. Letterbox is free.** 512-letterbox is statistically indistinguishable from
native (p=0.91) while still producing a fixed square input. **If a square input
is ever wanted for memory or speed, use letterbox and never squash.** The app
already passes native frames, which is the right default.

### Correction to the earlier claim

`docs/WIN_PLAN_2026-11-19.md` and a `src/main.py` comment carried a
**+8.43-point** figure (85.45% native vs 77.02% at 256-squash). That comparison
was fresh-native against a squash **cache** built on 8 Nov, and that cache had
drifted from live extraction — 15 of 40 sampled clips differ by up to 1.1 in
normalised coordinates. The real live gap is ≈3.4 points. The geometry fix
stands; its stated size was wrong by about seven points. Retracted in commit
`64f51a1`.

The headline 85.45% is unaffected: it was always measured on the native cache,
and live native reproduces it (84.94% e2e / 85.69% on-success on 1,255 clips).

## Latency: geometry is NOT a lever

Detector-only, median of medians over 12 timed rounds per configuration, warm-up
round discarded:

| geometry | ms/frame | clean range |
|---|---|---|
| native | 16.25 | 14.51–22.41 |
| 512 squash | 15.35 | 13.94–16.67 |
| 512 letterbox | 16.35 | 14.19–23.46 |
| 384 squash | 15.36 | 13.73–23.43 |
| 256 squash | 15.27 | 13.67–17.75 |

All within ~1 ms of each other on a quiet machine. **Downscaling the detector
input does not speed it up**, which is worth knowing because it is a natural
thing to try.

### The timing instability is machine-wide, not a geometry effect

An earlier pass measured native at 16, then 87, then 169 ms/frame. That looked
like a resolution effect and was not: in one round native 132.9, 512-squash
130.5 and 256-squash 130.2 ms/frame fired **simultaneously**, and the next round
everything fell to 15–17 ms. A final quiet round measured **all five**
configurations at 13.7–15.2 ms/frame. Any single-run timing on this machine is
unreliable; this is the same contention that once produced a retracted 133–199 ms
"FAIL" and a retracted 4,650 ms end-to-end figure.

**Consequence for the submission:** per-frame detector timing on this desktop is
not a stable number to quote. The on-device figures
(`docs/GPU_DELEGATE_2026-11-19.md`) are the ones that matter, and they were
taken six times with consistent results.
