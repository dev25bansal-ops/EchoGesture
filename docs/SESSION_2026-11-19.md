## The four results that matter

### 1. On-device latency is measured, and it is not 22.95 ms

The `results.csv` row was honest — it is labelled desktop x86 and says the phone
was never measured. It now has been, six samples across two installs, via the
app's own `AnalysisProfiler`:

```
analyse_p50 = 84-112 ms    detect_p50 = 80-109 ms    detect_p95 = 159-187 ms
fps = 8.7-11.6             convert_p50 = 4 ms        limit = ANALYSER
dropped = 76-82% of delivered frames
```

That is a **debug** build (`pkgFlags` contained `DEBUGGABLE`); release is faster
but unreadable on this phone because `run-as` needs a debuggable package and the
device has no root. 84–112 ms is a pessimistic bound, not a best case.

### 2. CHEEK is weak, but it is not confused with RAZOR2

Across all 32 cached CHEEK clips at native geometry: **75% (24/32)** correct,
and **RAZOR2 is predicted 0 times.** The wrong answers are PATIENT2 (4), MYSELF,
COMB2, PENNY, APPLE. Across the whole 1,251-clip test split, RAZOR2 attracts
only 8 clips total. CHEEK ranks 8th worst of 100 glosses; SINK and SCARF2
(50%) are worse.

The Kotlin feature port was verified against `src/features.py` to **2.4e-07**
max abs feature difference — the two are the same function. Ruled out:
idle padding, aspect ratio, hand scale/position/motion, MediaPipe VIDEO vs
IMAGE mode, signer leakage between splits.

### 3. Raising the acceptance threshold was tried and REVERTED

A 0.40 cut improves aggregate test accuracy from 92.1% to 97.4%. It was built,
and then reverted, because against the reported failures it does not help: the
CHEEK→RAZOR2 error arrived at **80.7% top-1 with the runner-up under 19.3%, a
margin of at least 0.614**, which a 0.40 cut would still accept. And in the
corpus, correct answers routinely land in the 0.2–0.3 margin band that a 0.40
cut would decline. See the correction note below — the specific replay figure
originally quoted here (49.9%, margin 0.216) came from an invalid measurement.

`MIN_MARGIN` ships at 0.15. The comment in `ResultPolicy.kt` records this so
nobody re-proposes it without re-running the evidence.

### 4. Window placement: investigated and CLEARED (retracted)

The user supplied a screen recording of the failing session (15.86 s). Cropped
to the camera preview and un-mirrored — which is what the analysis path sees,
since only the preview is mirrored — sliding a 3.7 s window gives:

```
  5.9-9.6  s     ELEVATOR1       39.2%   margin 0.272   cov  97%
  7.4-11.1 s     ELEVATOR1       49.9%   margin 0.216   cov 100%
  8.8-12.5 s     ELEVATOR1       22.3%   margin 0.004   cov  78%
```

**These numbers are WRONG and the conclusion drawn from them was retracted.**
The screen recording runs at about 2× speed — the app's own `Recording N.Ns`
counter advances 0.51 s per 1 s of video — so every window labelled 3.7 s was
really ~1.85 s of signing and every velocity feature was ~2× too high. Re-run on
the app's own clock, the replay reproduces neither the phone's answer nor a
stable one. See `docs/WINDOW_PLACEMENT_2026-11-19.md` and
`docs/ANALYSER_RATE_2026-11-19.md`.

What *did* survive, from a separate and valid measurement, is that the shipped
`SignSegmenter` is the best window policy tested (87.2% vs 84.2% for a proposed
replacement), so it should not be changed.

Three consecutive windows over the sign all say ELEVATOR1. The phone had taken a
**trailing** 7.7 s window ending at the tap and landed beside the sign.

Mirrored, the same window gives CHEW1 at 89% — so orientation is decisive too,
though the analysis path itself is doing the right thing.

**This does not explain CHEEK→RAZOR2**, which arrived with a high margin. The two
reports may have different causes. That is stated in the document rather than
papered over.

## The one thing still open

The user's report of confidently-wrong answers on the phone is **not explained**.
Four candidates have been measured and rejected:

| hypothesis | verdict | evidence |
|---|---|---|
| Kotlin feature-transform port bug | rejected | matches Python to 2.4e-07 |
| Window placement / segmenter | rejected | shipped segmenter 87.2% vs 84.2% for the proposed replacement |
| Low analyser rate / velocity scale | rejected | 18 real points scores 85.1%, same as corpus |
| Filming a laptop screen | rejected | hand size 1.00×, jitter 0.74× vs corpus |

**All four started from already-extracted landmarks or a hand-reconstructed
image.** None ran the phone's actual pixels through the reference pipeline, which
is the only remaining untested step.

**Two of my own analyses were invalid and were retracted in place**, not deleted:
a window-placement replay sized in video seconds when the screen recording runs
at ~2× speed, and a frame-rate table whose rates were mislabelled by 3.5×. Both
documents now state the correction first. A wrong finding that is quietly removed
is more dangerous than one that is labelled.

**The measurement that would settle it:** a debug-only frame dump in
`analyserCallback()`, so the phone's own analysis frames can be scored twice —
once by the app, once by `src/main.py`. `HandTracker.analyse()` already converts
each `ImageProxy` to a bitmap, so this is small and can sit behind the existing
diagnostics toggle.

## Environment notes that cost time

- torch is in `py -3.11`; **cv2 and mediapipe are not.** Use `py -3.11 -I` for
  torch-only work.
- cv2 + mediapipe + torch are together only in `C:/Python314/python.exe`, which
  must run **without** `-I` (its packages are in the user site-packages).
- The Android build needs `JAVA_HOME=D:\jdk17\jdk-17.0.21+9` and
  `ANDROID_HOME=D:\android-sdk`; the default JVM is Java 8 and is rejected.
- A release APK must be `zipalign -p 4` then `apksigner sign`; `jarsigner` alone
  produces an APK the device refuses with `Failed to extract native libraries`.
