## Already done today — do not redo

### The two changes that actually moved the score **[done, verified]**

**1. `predict()` was scoring on a resized geometry — fixed, but the size of
the win was initially overstated (corrected below).**

`predict()` called `clip_to_landmarks` with the default 256-squash, while the
nine FP16 members were trained on native-geometry landmarks. Fixed to
`size=None`.

**What the first version of this section said, and why it was wrong.** It
claimed the gap was **+8.43 points** (85.45% native vs 77.02% at 256-squash).
That number compared a **fresh** native cache against a **drifted** squash cache
built on 8 Nov — 15 of 40 sampled clips no longer match live 256-squash
extraction, by up to 1.1 in normalised coordinates. It was not a live
comparison.

**The measured truth**, full 1,255-clip test set, live extraction, every config
scored through the real pipeline (refusals counted wrong), with 95% CIs:

| geometry | end-to-end | on-success | vs native |
|---|---|---|---|
| **native** | **84.94%** ±1.98 | 85.69% | — |
| 512-letterbox | 85.10% ±1.97 | 85.65% | +0.16 pp, p=0.91 — **statistical tie** |
| 512-squash | 81.59% ±2.14 | 84.07% | −3.35 pp, p=0.0003 |
| 384-squash | 81.36% ±2.15 | 83.89% | −3.59 pp, p=0.0001 |
| 256-squash | 81.51% ±2.15 | 83.58% | −3.43 pp, p=0.0004 |

So the real gap is **≈3.4 points, not 8.43** — still a genuine, statistically
decisive win for native over any squash, and the fix is still correct. What was
wrong was the magnitude, and the squash geometries lose mostly through
**coverage/refusals** (25–31 low-coverage refusals vs 5–7), not through
misclassification.

A useful side result: **letterbox matches native (p=0.91)**. If a fixed square
input is ever needed for speed or memory, use letterbox and never squash.

Reproduce: `.scratch/measure_geometry_fullset_2026-11-19.py`; artifact
`.scratch/geometry_fullset_2026-11-19.json`.

**2. The MediaPipe GPU delegate was never enabled — enabled, ~2× faster.**

`HandTracker.create()` set no delegate at all, so the detector ran the default
CPU path. MediaPipe 0.10.14 exposes only `Delegate.CPU` and `Delegate.GPU`
(verified with `javap`; no NNAPI in this version). Now GPU-first with a CPU
fallback, confirmed on device by `HandLandmarker delegate=GPU` in logcat.

Four clean runs on the Vivo V2404, each a fresh process:

```
CPU:  detect p50 80-109 ms  p95 159-187 ms   8.7-11.6 fps   76-82% dropped
GPU:  detect p50 34-45 ms   p95 46-54 ms    19.2-25.0 fps   15-30% dropped
```

Against the 50 ms budget the detector goes from 3.2-3.7× over to **at or
inside** it. Full record: `docs/GPU_DELEGATE_2026-11-19.md`.

## The honest state of the project

The model is good: **85.45% top-1 on signers it has never seen**, 16.3 MB,
fully offline, inside every size and latency budget that was measurable. The
weakness is not the model — it is a handful of glosses and a capture window that
can land in the wrong place.

For the judges, the strongest thing you have is not the accuracy number. It is
that you can say, for every claim, what was measured, on what, and where it
breaks — including the two things that are genuinely bad (per-frame cost on the
phone, and the weakest signs). Almost no hackathon team will have that, and the
script's Beat 4 is where you show it off.
